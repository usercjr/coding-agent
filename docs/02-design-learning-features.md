## 零、先定一条设计原则

把下面这句话钉死，后面所有取舍都从它推导：

> ### 事实归工具，叙述归模型。
>
> 凡是「能算出来、算错了就是错」的东西（有哪些函数、谁调用谁、文件多少行、用户上次答错了什么），
> 一律由**工具**产出；凡是「要组织语言、要因材施教」的东西，交给**模型**。

违背它的典型反例：让模型自己读文件总结调用链 —— 它会编，而且你**无法验证**它编了。

## 一、新能力该放在哪一层？（核心 trade-off T1）

本项目有四个扩展位，选错位置是最常见的设计错误。判据：

| 扩展位 | 适合放什么 | 代价 | 本项目例子 |
| --- | --- | --- | --- |
| **Tool**（`agent/tools/*.py`） | 需要**确定性本地计算**的事实 | 要写代码、要测；占用模型的工具槽位和 schema 上下文 | `read_file`、拟新增的 `codemap` |
| **Skill**（`skills/*/SKILL.md`） | 需要**约束模型行为/流程**的规范 | 纯 prompt，软约束，模型可能不照做 | `teaching`、`code-review` |
| **Slash**（`main.py` `COMMANDS`） | **用户入口** / 会话状态开关 | 只在 CLI 层，agent 自己调不到 | `/teach`、`/auto` |
| **Hook**（`agent/hooks.py`） | **不可绕过的横切强制** | 对所有工具调用生效，容易误伤；调试难 | 5 层安全 |

**推荐心法**：
一个新教学功能，先问自己三句话 ——
1. 它要产出「不能错的事实」吗？→ 是，就得有 Tool。
2. 它要改变 agent 的**说话方式**吗？→ 是，就得有 Skill。
3. 用户要能手动触发它吗？→ 是，就得有 Slash。

所以一个完整的教学功能**常常是三层各出一块**，而不是「写个工具就完了」。

> ⚠️ 反面诱惑：「每轮结束强制出题」看起来该用 Hook。
> 但 Hook 拦的是**工具调用**，不是**对话轮次**，而且它返回字符串就等于「拦截」。
> 用 Hook 做教学强制 → 要么位置不对，要么会把正常工具调用拦死。
> **结论：这条用 Skill + Slash 实现，不要碰 Hook。** 这是个值得记住的「边界认知」。

## S1 · `codemap` 工具：把代码算成事实表

### 职责
给定一个目录或文件，**静态分析**出：有哪些模块、每个模块里有哪些顶层函数/类、
函数之间谁调用谁、模块之间谁 import 谁，并给出**建议阅读顺序**。

### 关键 trade-off（T2）：AST 静态分析 vs 直接丢给 LLM 读

| 方案 | 优 | 劣 |
| --- | --- | --- |
| `ast` 静态分析 | 准确、便宜、**可单元测试**、输出稳定 | 只支持 Python；看不见动态调用 |
| 整文件喂 LLM | 跨语言、懂语义、能理解意图 | 贵、会幻觉、长文件会漏、结果不稳定 |
| **AST 产事实 + LLM 做讲解**（推荐） | 既准又能讲 | 两段式，要设计中间数据结构 |

> 📌 **本项目自身就是 AST 的反例**：`agent/tools/base.py` 的 `_REGISTRY` 是运行时注册，
> `tool.execute(**args)` 这行 AST 只能看到「调了某个对象的 execute」，**看不出实际跑的是哪个工具**。
> 所以 `codemap` 的输出必须**老实标注自己的盲区**（动态分发、`getattr`、注册表），
> 否则它会教给学习者一个错误的心智模型 —— 这比不教还糟。

### 建议的输出数据结构

先定结构再写代码。建议 `codemap` 内部算出这样一个 dict，再序列化成**给模型看的紧凑文本**：

```
{
  "modules": [
    {"path": "agent/loop.py", "lines": 218, "doc": "模块 docstring 第一句",
     "defs": [{"name": "_agent_loop", "kind": "function", "line": 112, "args": ["msgs","allowed","compress"]}, ...]}
  ],
  "imports": [["agent/loop.py", "agent/tools/base.py"], ...],   # 模块依赖边
  "calls":   [["agent/loop.py:run", "agent/loop.py:_agent_loop"], ...],  # 函数调用边（同文件内可靠，跨文件尽力）
  "unknown": ["agent/loop.py:163 动态分发 tool.execute(**args)"]          # 明确标注盲区
}
```

### 签名草图（函数体留给你写）

```python
# agent/tools/codemap.py
def codemap(path: str = ".", depth: str = "outline") -> str:
    """扫描 path 下的 .py，返回结构化的代码地图文本。
    depth: "outline"=只要模块和定义 | "calls"=额外给调用边 | "order"=额外给建议阅读顺序
    """

def _scan_file(file_path: str) -> dict:
    """解析单个文件 → {"path","lines","doc","defs":[...]}"""

def _collect_edges(tree, module_path: str) -> tuple[list, list]:
    """从一棵 AST 里收集 (import 边, 调用边)。"""

def _reading_order(modules: list, imports: list) -> list[str]:
    """按依赖关系给出建议阅读顺序（被依赖得多的、底层的先读）。"""
```

### 动手前先想清楚这几个问题（别急着查文档）

1. 用 `ast` 遍历一棵语法树，「找出所有顶层函数」和「找出某个函数内部调用了谁」，
   这两件事在遍历策略上有什么**本质区别**？（提示：一个看树的第一层，一个要往下钻）
2. `_reading_order` 本质上是什么经典算法？如果模块之间有**循环依赖**（A import B，B import A），
   你的算法会死循环还是能兜住？
3. 一个 500 行的文件，`codemap` 输出应该多长？如果输出比原文件还长，这个工具就失去意义了 ——
   你打算用什么规则压缩？

## S2 · `/explain`：分层讲解

### 职责
用户说 `/explain agent/loop.py` 或 `/explain _agent_loop`，agent 按**固定的四层**讲，
**每层讲完停下来问「继续吗 / 哪里不清楚」**，而不是一口气倒完。

### 四层递进（这是教学设计，不是技术设计）

| 层 | 内容 | 为什么是这个顺序 |
| --- | --- | --- |
| L1 一句话 | 这个模块/函数在整个系统里**承担什么角色** | 先给钩子，没有全局位置感，细节记不住 |
| L2 结构 | 它由哪几块组成、数据怎么流 | 建立骨架 |
| L3 关键决策 | **为什么这么写**、不这么写会怎样、有什么 trade-off | 这是唯一真正值钱的一层 |
| L4 逐行 | 具体语法细节 | 只在用户要求时才进 |

> 多数 AI 讲代码的失败模式是：**直接从 L4 开始**，逐行翻译代码成中文。
> 学习者听完会觉得「每句都懂了，合起来不知道在干嘛」。

### 实现分工（印证前面的 T1）

- **Tool**：不用新增，调用 S1 的 `codemap` 拿事实。
- **Skill**：新增 `skills/explaining/SKILL.md`，写死这四层流程 + 「一次只讲一层，讲完必须停」。
- **Slash**：`main.py` 的 `COMMANDS` 里加一条 `"explain"`，prompt 模板里要求先 `load_skill("explaining")` 再 `codemap`。

> 💡 注意 `main.py` 现在的 `COMMANDS` 是**纯字符串模板**（`prompt 宏`）。
> `/explain` 能不能完全用一条模板搞定？还是需要在 `handle_slash` 里写分支？
> 想一想：哪种更符合现有设计、哪种更容易扩展到 `/quiz`、`/breakit`？
> （这里有个真实的重构信号：`COMMANDS` 可能该从 `dict[str, str]` 升级成 `dict[str, 带元信息的结构]`。）

## S3 · `/quiz`：出题、判定、记掌握度

### 职责
1. 针对刚学的模块出 2–3 道题（偏「为什么这么设计」「如果去掉 X 会怎样」，不是「这行干啥」）；
2. 用户答完，**判定对错并给出差在哪**；
3. 把结果写进**学习状态文件**，形成掌握度。

### 关键 trade-off（T4）：怎么判对错？

| 方案 | 评价 |
| --- | --- |
| 关键词匹配 | 自然语言答案根本不可能靠关键词判，会大量误判 → ❌ |
| 让主模型顺手判 | 它刚出完题又自己判，会「护短」，倾向于判对 → ⚠️ |
| **独立的 LLM-as-Judge**（推荐） | 单独一次调用、只给「题 + 标准答案要点 + 用户答案」，不给对话历史 → 判得更严 |

👉 **直接复用 `eval/run_eval.py::check_judge` 的套路**：一个干净的 prompt，只回 PASS/FAIL + 理由。
这是本项目已有的轮子，能省掉一半工作量，而且证明了你的 eval 模块设计是可复用的。

### 关键 trade-off：学习状态存哪？

| 方案 | 优 | 劣 |
| --- | --- | --- |
| 不存，只在对话里 | 零成本 | 关掉就没了，无法复习、无法统计 |
| 追加进 `memory.md` | 复用现成工具 | 扁平文本，**没法按知识点查/更新分数** |
| 独立 JSON（推荐） | 结构化、好查好更新、能支撑 S5 复习调度 | 要新写读写逻辑；得加进 `.gitignore`（个人数据） |

### 建议的学习状态结构

```
{
  "topics": {
    "agent/loop.py::_agent_loop": {
      "asked": 3, "passed": 2, "last_at": "2026-10-26",
      "weak_points": ["没说清为什么 compress 只给主 agent"]
    }
  }
}
```

`weak_points` 是最有价值的字段：它让下一次 `/explain` 能**针对性地**先补上次的漏洞。

### 签名草图

```python
# agent/tools/quiz.py
def quiz(topic: str, n: int = 3) -> str:
    """针对 topic 生成 n 道检验题（只出题，不给答案）。"""

def grade(topic: str, question: str, answer: str) -> str:
    """判定用户答案，返回「通过与否 + 差在哪」，并更新学习状态。"""

# agent/learning_state.py

def record(topic: str, passed: bool, weak_point: str = "") -> None: ...

    """返回掌握最差的 k 个知识点（给 /due 和下次讲解用）。"""
```

1. 出题这件事**需要工具吗**？模型本来就会出题 —— 那 `quiz` 这个 Tool 存在的理由到底是什么？

## S4 · `/breakit`：破坏式学习（最被低估的一个）

### 职责
agent 在**一个隔离的 git worktree** 里，把某个文件**故意改坏一处**（删掉一行边界保护、
改错一个判断条件），让用户去找：哪里坏了？会导致什么后果？为什么原作者要写这一行？

> 这是整套方案里**教学效率最高**的一个。因为它直接命中
> `skills/teaching/SKILL.md` 里那条「用后果驱动理解」。
> 而且它正好验证了你那些「保护性代码」的价值 —— 比如 `maybe_compress()` 里
> 「recent 不能以孤儿 tool 消息开头」那个 while 循环，光讲没感觉，把它删掉跑一次就全懂了。

### 关键 trade-off（T3）：在哪里改坏？

| 方案 | 优 | 劣 |
| --- | --- | --- |
| 直接改用户工作区 | 最真实 | 危险，要自己回滚，可能冲掉未提交改动 |
| 复制到临时目录 | 安全 | 丢失 git 上下文，没法 `git diff` 看「坏在哪」 |
| **git worktree**（推荐） | 安全 + 保留 git：可 `git diff` 对照、可一键丢弃 | 看不到未提交的改动，**必须提醒用户先 commit** |

👉 **直接复用 `agent/loop.py::_run_in_worktree`**（它已经会建 worktree + `set_cwd` 路由文件操作）。
你要补的是「破坏 + 出题 + 揭晓」这一层，以及 worktree 的**清理**
（现在的 `_run_in_worktree` 建了不删，`.worktrees/` 会越堆越多 —— 这是个已存在的小债）。

### 想清楚
- 「改坏」应该让**模型自由发挥**，还是给它一份**破坏类型清单**（删边界检查 / 改比较符 / 调换参数顺序 / 去掉 try）？
  哪种更可控、哪种更有教学价值？
- 用户猜完之后，怎么**揭晓**最有效？直接说「我改了第 103 行」，还是先让他自己跑一下看现象？

## S5 · `/due` 间隔复习

基于 S3 的学习状态，按「上次通过时间 + 通过率」挑出该复习的知识点出题。
最简规则就够用（不要上来就搞 SM-2 算法）：**答错的 1 天后复习，答对的 3 天 → 7 天 → 14 天**。

## S6 · 教学质量评测（简历向的大杀器）

现在 `eval/` 只量化「任务成功率」。教学模式是本项目的差异化卖点，**但它完全没有被量化**。

### 思路
新增一类 `kind="teach"` 的用例：用**第二个 LLM 扮演学生**（给它固定人设：
「你是初学者，会先给一个有明显缺陷的答案」），和被测 agent 对话 3–5 轮，
再用 judge 按 rubric 打分。

rubric 可以非常具体，例如：
- ❌ 是否直接给出了完整可运行的实现代码？（给了 = FAIL，这是红线）
- ✅ 是否先提问引导？
- ✅ 是否给了 trade-off 而不是单一「标准答案」？
- ✅ 是否出了检验题？

### trade-off
- 成本高（一道题要十几次 API 调用）、结果有随机性（要跑多次取平均）；
- 但这是**整个项目最能讲的一点**：你不只做了教学模式，你还**证明了它有效**。

### 现有 harness 的障碍
`eval/run_eval.py::run_one` 现在是**单轮**的（`run_subagent(task)` 一次返回）。
多轮教学评测需要一个能来回对话的 runner。
👉 想一想：这个改动会不会牵动 `run_subagent` 的签名？能不能**不改动它**而在外面包一层？
（这正是 `skills/teaching/SKILL.md` 里说的「涟漪效应」的真实案例，值得专门练一次。）

## 三、推荐的落地顺序

```
S1 codemap ──→ S2 /explain ──→ S3 /quiz ──→ S5 /due
                                    └────→ S6 教学评测
S4 /breakit （独立，随时可插队，性价比极高）
```

先做 **S1 + S2**，做完就能立刻感受到「讲解不幻觉了」；
再做 **S4**，它工作量最小但教学效果最猛；
然后 **S3 + S5** 把状态补上；**S6** 留到最后当收尾。
